# Decision Interview

> 원작: 정준 · 수정: jake-tt (chatforge의 도구와 경로에 맞게 재작성)

구현 전에 사용자가 결정을 효율적으로 내리도록 돕는다. 소크라테스식으로 한 번에 날카로운 질문 하나를 하되, 그 전에 저장소에 이미 있는 결정을 찾아 질문을 줄인다.

## 시작

요청을 분류한다.

- **Brownfield**: 기존 동작을 바꾸거나 확장하거나 뒤집는다 → 기존 결정을 먼저 찾는다.
- **Greenfield**: 새 동작이나 영역을 만든다 → 인접한 결정을 먼저 찾는다.

첫 질문 전에 검색한다.

```bash
python scripts/decisions.py find --query "<도메인 키워드>"
python scripts/decisions.py find --path <관련 소스 경로>
python scripts/decisions.py find --test <관련 테스트 경로>
```

관련 경로를 모르면 코드를 먼저 살펴 도메인을 파악하고 다시 검색한다. `decision-docs/specs/`, `decision-docs/adrs/`도 파일명과 frontmatter로 훑는다.

## 질문 규칙

- 한 번에 하나만 묻는다.
- 추천 답을 먼저 제시하고, 필요하면 트레이드오프가 있는 선택지 2~3개를 준다.
- 코드, 테스트, 결정 기록, spec, ADR로 답할 수 있는 것은 묻지 않고 직접 확인한다.
- 구현, 테스트, spec, ADR, 작업 범위 중 하나라도 바꾸는 결정만 묻는다.
- 남은 불확실성이 계획을 바꾸지 않으면 멈춘다.

## 결정의 종류

가장 작은 쓸모 있는 단위로 기록한다.

- **제품 동작**: 사용자에게 보이는 흐름, fallback, 검증, 순서, 상태 전이, 에러 동작
- **기술 경계**: 라이브러리·인프라 선택, API 경계, 저장 전략, 보안 경계
- **검증 정책**: 어떤 테스트나 검사로 이 결정을 증명할지
- **작업 경계**: 이번 조각에 넣을 것과 뺄 것, 병렬 작업이 가능한지

취향, 막연한 목표, 동작을 바꾸지 않고 바뀔 수 있는 구현 세부는 기록하지 않는다.

## 질문 형식

```text
정해야 할 것: <한 문장>
추천: <추천 선택지와 이유>
선택지:
- A: <트레이드오프>
- B: <트레이드오프>
- C: <트레이드오프, 선택>
질문: <직접적인 질문 하나>
```

기존 결정이 답을 제약하면 `DEC-*`, spec 경로, ADR 경로를 인용한다.

## 산출물

인터뷰 중 아래 파일을 만들고 계속 갱신한다. 첫 결정이 나오면 바로 만든다. 결정을 대화에만 남기지 않는다.

```text
decision-docs/plans/YYMMDD-<topic>-decision-interview.md
```

포함할 내용: Context, 검토한 기존 결정, 확정한 결정, 남은 질문, 검증 계획 인계, 작업 계획 인계, `records.jsonl`·spec·ADR 후보.

인터뷰가 끝나면 대화에 요약한다: 새 결정, 재사용하거나 유지한 기존 결정, 남은 결정, 추가할 `records.jsonl` 후보, 지금 `verification-plan`이 필요한지, spec·ADR로 승격할 후보.

구현 코드는 쓰지 않는다. 사용자가 요청하지 않으면 spec과 ADR도 만들지 않는다.

## 멈추고 물어볼 때

- 새 결정이 accepted 상태의 기존 결정, spec, ADR과 충돌할 때
- 사용자가 결정 정리를 건너뛰고 바로 구현하려 할 때
- 저장소에서 추론할 수 없는 비즈니스 판단이 필요할 때
- 답에 따라 작업이 spec인지, ADR인지, 구현인지, 할 일이 없는지가 갈릴 때
