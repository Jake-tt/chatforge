## 기준선을 만들며 고친 것

처음 실행에서 두 가지 문제가 드러나 고친 뒤 다시 쟀습니다.

1. **평가 실행기의 측정 버그**: httpx `ASGITransport`는 스트리밍 응답을 끝난 뒤에 한 번에 넘깁니다. 그래서 첫 실행에서는 40건 모두 "첫 delta까지" 시간이 "전체 턴" 시간과 같았습니다. 실행기가 앱을 로컬 소켓의 uvicorn으로 띄우게 고쳤습니다(`7f5ee3f`).
2. **라우터가 계정·지난 대화를 한 번도 요청하지 않음**: 기본값이 있는 필드는 JSON 스키마의 `required`에서 빠집니다. 제약 디코딩을 하는 Ollama는 required 필드만 쓰고 객체를 닫아 `needs_account`·`needs_past`를 켜지 않았고, 프롬프트가 "항상 채우라"고 한 `query`도 비웠습니다. 스키마의 모든 필드를 required로 보냅니다(`1a5d51a`, `DEC-BACKEND-ROUTER-SCHEMA-001`). 그러자 라우터가 느려져 8초 타임아웃에 절반이 걸렸습니다. 사용자 결정으로 Ollama만 기본 16초로 둡니다(`9814670`, `DEC-BACKEND-ROUTER-TIMEOUT-001`). 운영 Claude는 8초 그대로입니다.

| 지표 | 수정 전 (`7f5ee3f`) | 스키마만 수정, 8초 (`1a5d51a`) | 공식 (`9814670`, 16초) |
|---|---|---|---|
| 라우터 실패 | 6 | 20 | **0** |
| needs_account 정밀도 / 재현율 | – / 0.00 | 0.38 / 0.60 | 0.36 / **1.00** |
| needs_past 정밀도 / 재현율 | – / 0.00 | 0.33 / 0.20 | 0.56 / **1.00** |
| needs_search 정밀도 / 재현율 | 0.62 / 1.00 | 0.50 / 0.44 | 0.53 / 1.00 |
| needs_clarification 정밀도 / 재현율 | 0.50 / 0.20 | – / 0.00 | 0.44 / 0.80 |
| 모든 플래그 일치(한 턴 30 / 멀티턴 10) | 16 / 6 | – | 8 / 5 |
| 되묻기 비율 / 불필요한 되묻기 | 0.05 / 0.03 | 0.00 / 0.00 | 0.23 / 0.14 |
| 기대 사실 포함률 | 0.73 | 0.59 | 0.68 |
| 없는 번호 인용 비율 | 0.11 | 0.23 | **0.03** |
| 출처가 있는데 인용 0개 | 0.12 | 0.08 | **0.00** |
| 첫 delta p50 / 전체 p50 (초) | 9.2 / 16.0 | 13.9 / 21.3 | 11.7 / 16.9 |

해석: 이제 필요한 출처를 놓치지 않습니다(재현율 1.00). 대신 오탐이 늘어 모든 플래그가 맞는 비율은 떨어졌습니다. 특히 도움말 질문을 계정 질문으로 보내는 경우가 9건이고, 이때는 도움말 검색이 빠져 답이 나빠집니다(아래 표본 2·3번). 불필요한 되묻기도 0.03에서 0.14로 늘었습니다. 기대 사실 포함률이 0.73에서 0.68로 내려간 것은 되묻기로 끝난 턴이 늘어난 영향입니다. 기대 사실이 있는 케이스 중 되묻기로 끝난 것이 1건에서 4건으로 늘었고, 답한 턴만 보면 27/36(0.75)과 24/32(0.75)로 같습니다.
